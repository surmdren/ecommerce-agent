## 一、项目背景与目标

### 1.1 业务背景

亚马逊全球买家与中国卖家之间存在三重结构性障碍：**语言壁垒**（卖家英文能力不足）、**时差壁垒**（北京时间凌晨对应美东工作时间）、**成本壁垒**（专业英文客服月薪 $500–$1,500，超出中小卖家承受范围）。

亚马逊平台规则要求买家消息须在 **24 小时内**回复，超时将直接影响账号健康度（Account Health）及 Buy Box 获取率，进而对营业额造成实质性损失。

### 1.2 产品定位

面向**中国中小亚马逊卖家**的 AI 英文客服 SaaS，通过接入 Amazon SP-API，**自动拉取买家站内消息 → AI 生成专业英文回复草稿 → 卖家一键确认发送**，解决"看不懂、回不好、来不及"三大核心痛点。

### 1.3 业务目标

| 目标维度 | 具体指标 |
|---|---|
| 用户规模 | MVP 上线 3 个月内获取 200 付费用户 |
| 收入目标 | 月 MRR 达到 $15,000（约 150 用户 × $99） |
| 回复时效 | 用户平均消息回复时间从 8h+ 降至 30min 以内 |
| 回复质量 | AI 草稿采用率（用户不修改直接发送）≥ 70% |
| 账号健康 | 用户账号健康度违规率降低 80% |

### 1.4 PM 深度追问（关键边界待确认）

> 以下 5 个问题需在技术评审前与业务方对齐：

1. **消息拉取频率：** SP-API Notifications API 支持 Push（SQS/SNS）和 Pull 两种模式。MVP 是采用定时轮询（Pull）还是实时推送（Push）？推荐 Push 以保障时效性，但需申请额外权限。`[待确认]`
2. **卖家授权范围：** OAuth 授权时是否同时申请 `messaging:write` 权限（发送消息权限），还是 MVP 只读、后续再申请写权限？`[待确认]`
3. **多店铺管理：** 目标用户有 1–5 个店铺，订阅计划中"500 条消息"是所有店铺共享配额，还是每店铺独立？`[待确认]`
4. **AI 回复语气/风格：** 是否需要支持卖家自定义回复风格（如：正式 vs 友好）？MVP 是否提供默认模板参数？`[待确认]`
5. **合规边界：** "好评请求"场景需严格遵守亚马逊 CommunicationGuidelines（禁止激励性评价请求）。平台侧是否需要内置合规校验，防止用户滥用？`[建议 MVP 内置合规提示]`

## 二、目标用户与角色定义

### 2.1 用户角色矩阵

| 角色 | 描述 | 核心诉求 | 系统权限 |
|---|---|---|---|
| **卖家（主账号）** | 拥有亚马逊 Professional 账号的中国卖家，系统主要使用者 | 快速处理买家消息、不影响账号健康度 | 完整功能访问、账单管理、授权管理 |
| **子账号操作员** | 卖家团队成员（仓管、助理等），协助处理消息 | 查看消息、确认/修改 AI 草稿后提交 | 消息处理权限，无账单和授权管理 |
| **平台管理员（SaaS 运营方）** | 产品运营团队 | 监控系统状态、管理用户订阅、处理异常 | 后台管理全权限 |

### 2.2 用户画像（主角色）

- **人群：** 中国跨境电商卖家，主营亚马逊美国/欧洲站
- **规模：** 1–5 个店铺，月销售额 $5,000–$50,000
- **痛点等级：** 时差 > 语言 > 成本（按紧迫度排序）
- **技术接受度：** 中等，需要简洁的 UI 和清晰的操作引导
- **设备偏好：** PC 为主（店铺管理习惯），手机端为辅（随时查看通知）

## 三、业务范围说明（Scope）

### 3.1 MVP 必须做（In Scope）

| 模块 | 功能点 |
|---|---|
| 账号接入 | Amazon SP-API OAuth 2.0 授权，支持绑定多个亚马逊店铺 |
| 消息拉取 | 通过 SP-API 定时拉取 Buyer-Seller Messaging 站内消息 |
| 意图识别 | 使用 Claude Haiku 对消息进行 6 大场景分类 |
| AI 草稿生成 | 使用 Claude Sonnet 生成专业英文回复草稿 |
| 人工确认界面 | 卖家查看原始消息 + AI 草稿，可编辑后确认 |
| 一键发送 | 通过 SP-API Messaging API 发送已确认回复 |
| 消息状态管理 | 待处理 / 已确认待发 / 已发送 / 已忽略 状态流转 |
| 订阅计费 | Stripe 集成，支持 $49/月（500条）和 $99/月（无限制）两个套餐 |
| 用量统计 | 展示当月已用消息条数 / 配额，临近上限时提醒 |
| 基础通知 | 新消息到达时，发送邮件/站内通知提醒卖家处理 |

### 3.2 MVP 不做（Out of Scope）

| 功能 | 原因 |
|---|---|
| 全自动发送（无需人工确认） | 合规风险高，MVP 先建立用户信任 |
| Shopify / TikTok Shop 接入 | 聚焦亚马逊，避免分散研发资源 |
| 多语言支持（中文/日文等） | 目标买家为英语市场，后续扩展 |
| 数据分析 Dashboard | MVP 后根据用户反馈决定优先级 |
| 自动翻译（中文→英文模式） | 卖家直接使用 AI 草稿，无需中间翻译层 |
| 移动端 App | Web 响应式优先，App 列入 Phase 2 |

## 四、核心业务流程

### 4.1 主路径（Happy Path）

```
[卖家注册/登录]
      │
      ▼
[绑定亚马逊店铺] ──── OAuth 2.0 授权 ──── [SP-API 返回 Access Token]
      │
      ▼
[系统定时拉取站内消息] ──── SP-API Messaging API ──── [新消息入库]
      │
      ▼
[Claude Haiku 意图分类] ──── 识别 6 大场景 ──── [场景标签入库]
      │
      ▼
[Claude Sonnet 生成英文草稿] ──── 基于场景模板 + 消息内容 ──── [草稿入库]
      │
      ▼
[推送通知给卖家] ──── 邮件 / 站内通知
      │
      ▼
[卖家登录查看消息列表]
      │
      ▼
[卖家查看原文 + AI草稿] ──── 可选：编辑草稿
      │
      ▼
[点击"确认发送"] ──── SP-API 发送消息 ──── [消息状态更新为"已发送"]
      │
      ▼
[用量计数 +1] ──── 检查月度配额
```

### 4.2 异常路径处理

| 异常场景 | 触发条件 | 处理策略 |
|---|---|---|
| SP-API Token 过期 | Access Token 失效（有效期 1 小时） | 系统自动使用 Refresh Token 刷新；刷新失败则通知卖家重新授权 |
| 消息拉取失败 | SP-API 限流或网络异常 | 指数退避重试（最多 3 次）；失败后记录错误日志，下次轮询补偿 |
| 意图识别失败 | Claude API 超时或返回异常 | 标记为"未分类"，仍进入草稿生成流程；前端展示"场景：其他" |
| AI 草稿生成失败 | Claude API 错误或超时 | 消息标记为"草稿生成失败"，通知卖家手动处理；提供空白编辑框 |
| 发送消息失败 | SP-API 拒绝（权限不足/消息违规） | 展示具体错误原因；对于违规内容给出修改建议 |
| 月度配额用尽（$49套餐） | 当月消息数达 500 条 | 拦截新消息的 AI 处理；弹窗提示升级套餐；消息仍可手动处理 |
| 卖家账号被暂停 | 亚马逊封号 | SP-API 授权失效，系统自动标记店铺状态为"异常"并通知卖家 |

### 4.3 关键状态机（消息生命周期）

```
[新消息拉取]
    │
    ▼
[pending_ai] ──AI生成失败──► [ai_failed] ──► [需人工处理]
    │
  AI成功
    │
    ▼
[pending_review] ──卖家忽略──► [ignored]
    │
  卖家确认
    │
    ▼
[pending_send] ──发送失败──► [send_failed]
    │
  发送成功
    │
    ▼
[sent] ──────────────────────────────────── [终态]
```

## 五、功能模块需求

### 5.1 模块 A：用户账号与认证模块

#### A1 - 卖家注册/登录

- **前端端点：** Web（PC + 响应式移动）
- **支持方式：** 邮箱 + 密码注册；Google OAuth 登录（可选）
- **安全要求：** 密码最低 8 位含字母数字；登录失败 5 次锁定账号 15 分钟
- **后端逻辑：** JWT 无状态认证，Access Token 有效期 2 小时，Refresh Token 7 天

#### A2 - 亚马逊店铺授权绑定

- **前端端点：** 店铺管理页面
- **交互流程：**
  1. 卖家点击"添加店铺"
  2. 跳转至亚马逊 LWA（Login with Amazon）OAuth 2.0 授权页
  3. 卖家授权后回调，系统保存 `access_token` + `refresh_token` + `seller_id` + `marketplace_id`
- **支持市场：** 美国（US）、英国（UK）、德国（DE）、日本（JP）`[MVP 优先支持 US]`
- **权限范围（SP-API Scopes）：**
  - `sellingpartnerapi::messaging` （读取和发送 Buyer-Seller 消息）
  - `sellingpartnerapi::notifications` （接收消息推送通知）
- **多店铺：** 一个 SaaS 账号可绑定多个亚马逊店铺，统一管理
- **Token 管理：** Refresh Token 加密存储（AES-256）；后台自动定时刷新 Access Token

#### A3 - 订阅计划管理

- **套餐定义：**

  | 套餐 | 价格 | 消息配额/月 | 店铺数量上限 |
  |---|---|---|---|
  | Starter | $49/月 | 500 条 | 3 个 `[待确认]` |
  | Pro | $99/月 | 无限制 | 无限制 |

- **计费方式：** Stripe Subscription，支持信用卡（Visa/Mastercard/American Express）
- **计费周期：** 自然月（每月同日扣费）
- **试用期：** 免费试用 14 天（含 50 条消息配额）`[待确认是否提供]`
- **降级处理：** Pro 降级为 Starter 后，当月已超用消息不追溯；次月起生效限额

---

### 5.2 模块 B：消息拉取与同步模块

#### B1 - 消息定时拉取（轮询模式，MVP）

- **触发方式：** 后端 Cron Job，每 **5 分钟**轮询一次所有已绑定店铺 `[可配置]`
- **API 调用：** `GET /messaging/v1/orders/{orderId}/messages`（SP-API）
- **去重逻辑：** 以 `messageId` 为唯一键，已存在则跳过
- **存储字段：**
  - `message_id`、`order_id`、`buyer_name`（脱敏）、`message_body`、`message_time`
  - `shop_id`（关联店铺）、`status`（消息处理状态）

#### B2 - 实时推送（Phase 2，SP-API Notifications API）

- **方案：** 申请 `MESSAGING_NOTIFICATION` 事件，通过 AWS SQS 接收 Push 通知
- **优势：** 秒级延迟，替代轮询，降低 API 配额消耗
- **依赖：** 需 Amazon SP-API Notifications 权限审批（申请周期 1–4 周）

#### B3 - 消息列表展示

- **前端端点：** Web 消息中心页面
- **展示字段：** 买家名称（脱敏，仅显示首字母）、订单号、消息摘要（前 100 字符）、接收时间、处理状态、场景标签
- **筛选/排序：** 按状态筛选（待处理/已发送/已忽略）；按时间倒序排列
- **紧急标识：** 消息接收超过 **18 小时**未处理，展示红色"紧急"标签（距 24h 亚马逊 deadline 还剩 6h）

---

### 5.3 模块 C：AI 意图识别模块

#### C1 - 6 大场景分类

- **执行模型：** Claude Haiku（低成本，高速分类）
- **分类 Prompt 策略：** System Prompt 定义 6 个场景 + Few-shot 示例（每场景 3 条）
- **输出格式：** 结构化 JSON `{ "intent": "product_inquiry", "confidence": 0.92 }`
- **兜底逻辑：** 置信度 < 0.7 时，标记为 `other`，仍进入草稿生成流程

| 场景 ID | 场景名称 | 典型消息示例 |
|---|---|---|
| `product_inquiry` | 产品咨询 | "Does this come in size XL?" |
| `logistics_tracking` | 物流追踪 | "Where is my package? It's been 2 weeks." |
| `refund_return` | 退款退货 | "I want to return this, it doesn't fit." |
| `negative_review` | 差评申诉 | "I left a 1-star review, the product was defective." |
| `product_damage` | 产品损坏 | "The item arrived broken, what can you do?" |
| `review_request` | 好评请求 | 主动发送（合规版，无激励性语言） |
| `other` | 其他 | 不符合以上任一场景 |

#### C2 - 意图分类质量优化

- **用户反馈机制：** 卖家可在处理消息时标记"分类错误"，记录到训练数据池
- **定期回顾：** 每月统计分类准确率，低于 85% 时触发 Prompt 优化

---

### 5.4 模块 D：AI 回复草稿生成模块

#### D1 - 草稿生成逻辑

- **执行模型：** Claude Sonnet（高质量英文写作）
- **Prompt 设计原则：**
  - System Prompt：定义角色（亚马逊卖家客服代表）、语气（专业、友好、简洁）、约束（不承诺不确定信息）
  - User Prompt：传入`场景`+`买家原始消息`+`订单信息（可选）`
- **输出内容：** 完整英文回复正文（100–250 词）
- **场景差异化策略：**

  | 场景 | 草稿侧重点 |
  |---|---|
  | 产品咨询 | 准确描述产品特性，引导购买决策 |
  | 物流追踪 | 提供物流查询方式，表达歉意（如延误） |
  | 退款退货 | 清晰说明退换货流程，提供解决方案 |
  | 差评申诉 | 诚恳道歉 + 提供补救方案（禁止要求删除评价） |
  | 产品损坏 | 立即承诺补发/退款，收集证据照片请求 |
  | 好评请求 | 感谢购买 + 简洁请求留评（无激励语言，合规） |

#### D2 - 草稿编辑界面

- **前端端点：** Web 消息详情页
- **布局：** 左侧展示买家原始消息（支持中文机器翻译参考 `[待确认 API 供应商]`）；右侧展示 AI 草稿编辑框
- **编辑功能：** 富文本编辑（支持换行，不支持格式）；字数实时计数（亚马逊消息上限 `[待确认]`）
- **操作按钮：**
  - "重新生成"：重新调用 AI 生成新草稿（每条消息最多重试 3 次）
  - "确认发送"：提交草稿至发送队列
  - "忽略"：标记消息为已忽略，不发送

#### D3 - 合规校验（内置）

- 发送前自动扫描草稿中的高风险词汇：`"delete review"`, `"remove feedback"`, `"gift card"`, `"discount"` 等激励性词汇
- 检测到风险词时，弹窗警告提示卖家修改，不强制阻止发送（MVP 为软提示）

---

### 5.5 模块 E：消息发送模块

#### E1 - 发送逻辑

- **API 调用：** `POST /messaging/v1/orders/{orderId}/messages/buyer` （SP-API）
- **发送前校验：** Token 有效性 → 配额剩余 → 合规关键词检测
- **异步发送：** 进入消息队列（Bull/BullMQ）异步执行，避免前端等待超时
- **发送结果处理：**
  - 成功：更新消息状态为 `sent`，记录发送时间戳
  - 失败：更新状态为 `send_failed`，记录错误码，前端展示失败原因

#### E2 - 发送记录

- **存储字段：** `sent_at`、`sp_api_response_code`、`message_content_snapshot`（发送内容快照）
- **用途：** 合规追溯、用户查阅历史发送记录

---

### 5.6 模块 F：通知模块

#### F1 - 新消息通知

- **触发时机：** 新消息拉取入库后立即触发
- **通知渠道（MVP）：** 邮件通知（SendGrid/Resend）
- **通知内容：** 买家消息摘要 + 接收时间 + 跳转链接（直达该消息处理页）
- **免打扰设置：** 卖家可设置通知静默时段 `[待确认是否 MVP 必须]`

#### F2 - 紧急超时提醒

- **触发条件：** 消息未处理超过 18 小时（距亚马逊 24h 要求剩余 6h）
- **通知渠道：** 邮件（二次提醒）
- **前端标识：** 消息列表中该消息展示红色"⚠️ 紧急"标签

---

### 5.7 模块 G：用量与计费模块

#### G1 - 用量计数

- **计数规则：** 每条消息**成功发送**（状态变为 `sent`）时计数 +1；草稿生成不计数；发送失败不计数
- **计数周期：** 自然月，每月 1 日自动重置（Pro 套餐不限制，仍记录用于数据统计）
- **配额预警：** 使用量达 80% 时，站内 Banner 提示；达 100% 时发送邮件并拦截 AI 处理

#### G2 - Stripe 集成

- **支付流程：** Stripe Checkout（托管页面）完成支付，Webhook 同步订阅状态
- **Webhook 事件处理：**
  - `checkout.session.completed`：激活订阅，写入用户套餐
  - `invoice.payment_succeeded`：续费成功，重置月度配额
  - `invoice.payment_failed`：扣款失败，降级为免费模式（保留 7 天宽限期）
  - `customer.subscription.deleted`：取消订阅，套餐到期日后禁用 AI 功能

## 六、非功能性需求

### 6.1 性能要求

| 指标 | 要求 | 说明 |
|---|---|---|
| AI 草稿生成时延 | P50 < 5s，P95 < 15s | Claude Sonnet API 调用，含网络延迟 |
| 消息拉取延迟 | 新消息到达后 ≤ 10 分钟内入库 | 基于 5 分钟轮询周期 |
| 页面首屏加载 | < 2s（千兆宽带下） | Next.js SSR + CDN |
| API 接口响应 | P95 < 500ms（不含 AI 调用） | Fastify 后端 |
| 并发处理能力 | 同时处理 100 个店铺的消息拉取任务 | 通过消息队列实现异步解耦 |

### 6.2 安全要求

| 安全维度 | 具体措施 |
|---|---|
| SP-API Token 存储 | AES-256 加密存储，禁止明文写入数据库或日志 |
| 用户数据隔离 | 所有数据库查询强制附加 `seller_id` 隔离条件，防止越权访问 |
| API 鉴权 | 所有后端 API 使用 JWT Bearer Token 认证 |
| 速率限制 | 发送消息 API：每店铺每分钟最多 10 次；登录接口：每 IP 每分钟 5 次 |
| 数据传输 | 全程 HTTPS（TLS 1.2+） |
| 买家隐私合规 | 买家姓名脱敏显示（仅显示首字母 + ***）；不对外暴露买家联系方式 |
| 日志脱敏 | 日志中不记录 Token、买家消息原文、回复内容 |

### 6.3 可用性与扩展性

- **目标可用性：** 99.5%（月度）
- **SP-API 限流应对：** 实现令牌桶算法控制 API 调用速率，配合指数退避重试
- **多租户架构：** 数据库层面以 `seller_id` 隔离，为未来独立数据库（数据库分片）预留扩展接口
- **AI 模型可替换：** AI 调用层封装为抽象接口（Strategy Pattern），支持未来替换或叠加其他 LLM
- **i18n 预留：** 前端文案使用 i18n Key 管理（如 `i18next`），为未来多语言做好结构预留，MVP 仅实现中文界面

### 6.4 数据备份与恢复

- PostgreSQL 每日自动备份（Railway 托管），保留 7 天
- 关键业务数据（发送记录）额外每周全量导出至 S3 `[待确认]`
